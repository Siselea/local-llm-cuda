# CPU 侧 int8 行内核（`cpu_int8`）：设计、数值、实测，以及为什么默认关闭

日期：2026-11-15 · 实现：`src/cpu_matvec.cpp` · 配置：`cpu_int8`（0=关，1=按实测类型，2=Q4_K 也开）

---

## 1. 为什么要做

35B 的 24 个 CPU 驻留 MoE 层，每 token 的 host matvec 是 **0.84 ms × 24 = 20 ms**（§32.2），
有效带宽 **19.4 GB/s**（16.3 MB/层），而同机独立基准最好 22.8 GB/s、DRAM 纯读天花板 31–36 GB/s。
即：CPU 量化 GEMV 还有 ~1.5× 的头。

已有的取证（SPEC §29.2）说明瓶颈不是 DRAM：单核量化行内核只有 5.7 GB/s，而同线程纯 AVX2 读
同一批字节 15–18 GB/s，**去掉 x 载入和 FMA 的"纯解包探针"与完整内核同速** ⇒ 指令吞吐/解包，
不是带宽。所以思路是把 float MAC 换成 int8 MAC（`_mm256_maddubs_epi16` 一条指令 32 次乘加）。

## 2. 实现

### 2.1 激活的两级 int8 量化（`xq_build`）

单级 int8 的量化误差是 `d/sqrt(12) = amax/(127·√12)`，对 32 值一块约 **3e-3 相对**，太大
（GPU dp4a 当初量到 4.9e-3，会让 9B 第 6 个 token 漂移）。所以用**两级**：先量化主值，
再把残差量化一级，各自有独立的、每 32 值一个的 fp32 scale：

```
x̂ = d1·q1 + d2·q2          (q1, q2 ∈ int8, d1/d2 每 32 值一个)
Σ w·x̂ = Σ w·(d1·q1) + Σ w·(d2·q2)
```

同时按块的 32/16 值分组预存 **重构激活的和** `sx32` / `sx16`，供 Q4_K / Q6_K 的 bias 项用
（Q4_K: `-dmin·mn·Σx`；Q6_K: `-32·d·sc·Σx`）。量化器是 AVX2 向量化实现（`cvtps_epi32` 四舍五入、
`packs` 打包），一次 2048 宽激活 **2.1 µs**（第一版用了 `std::lrint`，它是真实函数调用，
11 ns/元素 ⇒ 14.7 µs，慢 7 倍，这个坑在下面 §5 记一笔）。

### 2.2 行内核

| 类型 | 每 32 值指令数（估算） | 说明 |
|---|---|---|
| Q4_K `avx2_dot_q4k_i8` | ~15 | 1 load + `and`/`srli+and` 得 lo/hi 两组 0..15（unsigned，直接喂 maddubs）；2 级激活各 1 次 maddubs+madd；8 个 int32 lane = 4 值部分和，乘 sub-block scale 后进 4 个独立累加器 |
| Q6_K `avx2_dot_q6k_i8` | ~22 | 6-bit 保持 unsigned（0..63，maddubs 第一操作数），`-32` 的偏移用 `-32·d·sc·Σx` 从 `sx16` 补回；一个 32 值向量里有 **两个** 16 值 scale，用 `[sa sa sa sa sb sb sb sb]` 的 blend 施加 |

分派规则（`int8_row_supported`）**只看量化类型与宽度**：
`Q6_K` 且 `n_in % 256 == 0` → int8（`cpu_int8 ≥ 1`）；`Q4_K` 同上但只在 `cpu_int8 = 2` 时用；
`Q5_K/Q5_1/Q8_0` 与奇数宽度永远是 fp32 行内核。没有任何模型名/层号分支。

## 3. 数值

`tests/test_cpu_moe.cpp` 新增了 int8 段（vs fp32 行内核的相对 L2，限 5e-5）：

| 用例 | rel_l2 | 结论 |
|---|---|---|
| Q4_K 行 (512×2048) | 2.19e-6 | PASS |
| Q6_K 行 (2048×512) | **1.06e-5** | PASS（与 GPU dp4a 的 1.05–1.96e-5 同量级） |
| 整层 `moe_forward_mt`（含 SiLU/加权合并） | 3.06e-5 | PASS |
| 原有 fp32 位精确性检查（`cpu_int8=0`） | 4.8e-7 / 2.8e-8 / 7.3e-8 | PASS（未变） |

`cpu_int8=0`（默认）时 `matvec_mt`/`moe_forward_mt` 走的就是原来的 fp32 内核，**逐位不变**。
四模型预测在 int8 打开时也正确（35B topk `69014` 在 A/B 的 5 次运行里全部一致）。

> 注：Q4_K 的 rel_l2 比 Q6_K 好一个量级，是因为 Q4_K 的 fp32 参照本身用 4 个累加器、
> 而 Q6_K 的 fp32 内核每行 1.4 条指令/元素（解包更贵）——不是 int8 精度差异。

## 4. 实测（含"以前为什么没默认开"的修正）

### 4.1 孤立内核（L1 热、单线程、`tools/dbg_i8_alu.cpp`，每行 2048 值，20 万次）

| 内核 | ns/行 | 相对 |
|---|---|---|
| fp32 Q4_K | 184–200 | 基准 |
| int8 Q4_K | 208–242 | **慢 12–21%（负结果）** |
| fp32 Q6_K | 288–300 | 基准 |
| int8 Q6_K | **229** | **快 1.31×** |

为什么 Q4_K 的 int8 反而慢：Q4_K 的 fp32 内核只要 0.875 条指令/元素（`cvtepu8_epi32` 8 值一发），
而 Q6_K 的 fp32 内核要 1.4 条指令/元素（6-bit 的 qh 位拼接）。int8 把两者都压到 ~0.47/0.69
条指令/元素，但 Q4_K 原本就不贵，换成 int8 反而多付了"标量 scale 广播 + 两级量化"的开销。
⇒ `cpu_int8=1` 只对 Q6_K 生效，`=2` 才含 Q4_K（供 A/B，默认不建议）。

### 4.2 引擎内单层（`ENGINE_DBG_MOE_PHASES=1`，35B，24 个 CPU 层，单位 ms/层）

| 相位 | fp32 (`cpu_int8=0`) | int8 Q6_K (`=1`) | Δ |
|---|---|---|---|
| phase A（gate+up，Q4_K） | 0.456–0.614（中位 0.491） | 0.483–0.828（中位 0.503） | 噪声内（同一条代码路径） |
| **phase B（down，Q6_K）** | 0.318–0.448（中位 0.346） | **0.310–0.383（中位 0.326）** | **−6%** |
| merge | 0.008–0.097 | 0.019–0.059 | 噪声 |

即"phase B 快 6%"，折算到 token：phase B 占 24 × 0.346 = 8.3 ms，−6% ⇒ **−0.5 ms/token**
（37.98 ms 的 1.3%）。这与"DRAM 已经贴着 19.4 GB/s、指令数减半只换来少量收益"的判断一致：
**CPU 路径在 9 线程下已经不是纯指令受限**，int8 能省的指令时间只占一部分。

### 4.3 隔离单层（`tools/bench_cpu_layer.cpp` layer 模式，24 个副本轮转 = 真 DRAM 流，9 线程）

这是与引擎内 `cpu::moe_forward_mt` **完全相同的计算**（35B 的 hidden=2048 / inter=512 / top-8，
gate+up Q4_K + down Q6_K），也是任务书优先级最高的"单层 host matvec"指标。9 次交错配对：

| `cpu_int8` | min ms/层 | 中位 ms/层 | 配对中位（on/off） |
|---|---|---|---|
| 0（fp32） | 0.762 | 0.811 | — |
| **1（Q6_K int8）** | **0.714** | **0.734** | **−10.1%**（min −30.3%，max +1.0%） |
| 2（Q4_K 也 int8） | 0.808 | 0.848 | +4.6%（更慢，Q4_K 的 int8 内核不划算） |

相位级（`ENGINE_DBG_MOE_PHASES`，24 层中位）：phase B（down，Q6_K）**0.346 → 0.326 ms（−6%）**，
phase A（Q4_K，代码路径未变）在噪声内。线程数扫描（int8=1，min of 3）：6 线程 0.905、
**9 线程 0.717**、10 线程 0.714、12 线程 0.915 ms —— 默认 9 线程仍是最优（10 线程持平）。

### 4.4 端到端（35B decode，同二进制、环境变量开关、交错 A/B）

见 `GENERAL-OPT-REPORT.md` 的最终表。**决策依据按任务书优先级取隔离单层指标（−10.1%）**：
端到端只有 −0.5 ms/token 量级（24 层 × 0.08 ms），在本机 ±10% 的漂移下有窗口才能分辨，
不作为默认开关的判据。

## 4.5 结论：**默认开启 `cpu_int8=1`**

| 判据 | 数据 | 是否达标 |
|---|---|---|
| 单层 host matvec 更快（任务书优先级 #1） | 0.762/0.811 → **0.714/0.734** ms（min/中位），配对中位 **−10.1%** | ✅（>5% 门槛） |
| 引擎内相位 | phase B 0.346 → 0.326 ms（−6%） | ✅ |
| 数值正确 | 单测 rel_l2：Q4_K 2.19e-6、Q6_K 1.06e-5、整层 3.06e-5（限 5e-5） | ✅ |
| 四模型预测 | 35B top-1 `69014` 在 int8 打开时多次复现（两种放置）；Coder 的 CPU 专家是 **Q5_K/Q5_1**（无 int8 内核，行为不变） | ✅ |
| 不劣化其它量化类型 | Q5_K/Q5_1/Q8_0/奇数宽度永远走 fp32 内核（`int8_row_supported` 只看类型与宽度） | ✅ |
| `cpu_int8=0` 可一键回退 | 逐位回到原 fp32 内核（单测已固定 `cpu_int8=0` 位精确段） | ✅ |

## 5. 负结果 / 踩过的坑（如实）

1. **sub-block 索引 bug（已修）**：第一版把"全局 32 值块下标"同时用于 `scf[sub]/mnf[sub]`（应为
   block 内的 0..7），导致只有第 0 个 256 值块正确、后面读到越界的 scale → NaN。是
   `tools/dbg_i8.cpp`（把 `src/cpu_matvec.cpp` include 进来的最小复现）定位的。
2. **单累加器是错的**：int8 内核第一版 4 组共用一个 `__m256 acc`，16 条串行 FMA 链（4–5 cycle/条）
   ⇒ 295 ns/行（比 fp32 慢 60%）。改成 4 个固定名字的累加器后 208 ns；用
   `__m256& a = cond ? acc0 : ...` 这种"按索引取引用"的写法会让编译器把累加器**溢出到栈**
   （这就是第一版慢的第二个原因），必须靠宏展开成固定变量名。
3. **`std::lrint` 是函数调用**：量化器第一版 14.7 µs/2048 值（11 ns/元素），换成
   `cvtps_epi32` + 向量化后 2.1 µs。
4. **加深预取（当前行 → 前面第 1 行 T0 + 第 2 行 T1）**：孤立 matvec 上最小时间从 13.2 → 19.0
   GB/s（但同代码重跑 6.3–23.9 GB/s，完全被机器负载支配），端到端无法验证 ⇒ **已回退**，
   保持原来的"本行 T0 + 下一行 T1"。

## 5.5 判据的严格表述：int8 的收益窗口很窄

int8（CPU 行内核或 GPU dp4a）**不会**自动带来提速，它只在下面三个条件同时成立时才划算，
本机实测把三者量化成了可对照的数：

| 条件 | 本机实测 | 含义 |
|---|---|---|
| ① 该路径是**指令受限**，不是带宽受限 | CPU：纯读天花板 29.7 GB/s vs 量化行内核 21 GB/s（9 线程，同一批字节）；去掉 FMA 的"纯解包探针"与完整内核同速 ⇒ 指令受限 | 如果是 DRAM 受限，砍指令只会剩下等待，收益 ≈0（这就是 `layer` 全层只赢 −10% 而不是 −40% 的原因） |
| ② 该量化类型的 **fp32 内核指令重** | Q6_K 1.4 指令/值（6-bit 的 qh 位拼接）⇒ int8 赢 1.31×；Q4_K 0.875 指令/值 ⇒ int8 **输** 12–21% | "按量化类型选内核"，不能一刀切 |
| ③ **SIMD/张量单元未饱和、且精度预算允许**（int8 需要两级量化才能到 1e-5） | GPU：fp32 FMA 5.75 T-MAC/s，dp4a 13.8，int8 cuBLAS 12.0，**fp16 cuBLAS 12.8** ⇒ GPU 上 int8 甚至不如 fp16（prefill-fast 实测） | GPU 侧优先 fp16 tensor core；CPU 侧 int8 只在 ①②③ 都满足时 |

反过来说：**"int8 不是免费的"**——它用两级量化的额外访存/指令、以及 ~1e-5 的数值误差，
换取 2–4× 的乘加吞吐。只有当乘加是瓶颈（①②）且精度够（③）时才是正收益。本机的结论：
**CPU 侧 Q6_K host 行 = 正收益（−10%）；CPU 侧 Q4_K = 负收益（+4.6%，因此 `cpu_int8=2` 不默认）；
GPU 侧 = 用 fp16 tensor core 而不是 int8。**

## 6. 状态与下一轮

- **默认 `cpu_int8=1`**（Q6_K 行 int8，其余类型 fp32）；`ENGINE_CPU_INT8=0` 可完全回退，
  `=2` 打开 Q4_K 的 int8（实测更慢，仅供 A/B）。
- 仍值得做的下一轮（收益排序）：
  1. **权重 repack**：load 时把 Q4_K/Q6_K 的 host 权重重排成"nibble 已分离 + scale 已展开成 fp32"
     的 AVX2 友好布局。现在每行每 256 值要重新做 8 次 `scale_min`（分支）+ 2 次 fp16 转换；
     repack 后这些全部消失，且可以省掉 Q4_K 的 12 B scale 表的位解包。代价是 host 内存
     +5–25%，DRAM 流量不变（仍是 0.56 B/值），对 35B 的 407 MB host 权重是可接受的。
  2. **两行/四行融合的内核**（一次 x 量化，四个专家行共享）——CPU 侧 cache 复用。
  3. 把 int8 反向用于 Coder（它的 CPU 层是 Q5_K/Q5_1，目前没有 int8 内核，需要先做 Q5_K 的
     `maddubs` 版本；参考 §29 实测 Q5_K 的 fp32 单核 5.7 GB/s，收益可能比 Q6_K 大）。

## 7. 复现

```bash
# 数值单测（含 int8 段）
./build/test_cpu_moe.exe
# 孤立内核 ALU 对比（Q4_K 慢 / Q6_K 快的来源）
python -m ziglang c++ -std=c++17 -O2 -Iinclude tools/dbg_i8_alu.cpp src/config.cpp -o build/dbg_i8_alu.exe
./build/dbg_i8_alu.exe
# 35B 每层相位（打开 int8 后 phase B 应快 ~6%）
ENGINE_CPU_INT8=1 ENGINE_DBG_MOE_PHASES=1 ./build/test_gen.exe <35B.gguf> "760" 2
# 引擎内 A/B
ENGINE_CPU_INT8=1 ./build/test_gen.exe <35B.gguf> "760" 17   # vs ENGINE_CPU_INT8=0
```
