# decode 期间 CPU 占用实测报告（CPU-OCCUPANCY）

**日期**：2026-11-16/17 · **机器**：i5-10400F（6 物理核 / 12 逻辑核）· 32 GB · RTX 3060 12 GB · Windows 11
**触发问题**（用户观察）：「生成的时候 CPU 并没有按照选择核心满载，而是如同正常待机一样，跟没有参与计算一样」
**测量工具**（只读计数器，不改代码）：`tools/cpu_probe.py`（NtQuerySystemInformation 每逻辑核
idle/kernel/user + GetProcessTimes 进程 CPU + nvidia-smi，50 ms 采样 + 1 s 汇总）、
`tools/bench_cpu_layer.cpp`。decode 窗口由引擎 stderr 的 `[time] prefill …` 起、`[time] decode …` 止。
35B/Coder 的 host-GEMV 由 `ENGINE_DBG_CPUEXEC` 的 `(last 25: X ms)` 窗口给出。

---

## 0. 一句话结论

> **CPU 确实在参与计算，而且线程池确实用满了 9 个线程；只是它对每个 token 的贡献是"占空比 45% 的
> 0.75 ms 突发"，OS 的 1 秒采样把它摊平成"每核 40–55%"，所以任务管理器看起来没有满载。**
>
> - **9B / 0.5B（全 GPU dense）：进程 CPU ≈ 0.98–1.0 核（只有一个提交线程在忙），整机 ~8%。这是
>   完全正常的**——它们本来就不用 CPU 算，算的是 GPU（99% util / 170 W）。线程池根本不会创建
>   （总线程数 14，和 35B 的 22–25 对比即知）。
> - **35B（16 GPU 层 + 24 CPU 专家层，threads=9）：进程 CPU ≈ 4.0–4.3 核**（12 线程的 34–36%），
>   每秒稳定；CPU 阶段 = 24 层 × 0.755 ms = **18.2 ms / token（占 token 时间 45.5%）**，其余 55%
>   在等 GPU（GPU util 只有 38–39%，符合"CPU 是瓶颈、GPU 在等"）。
> - **Coder（17 GPU 层 + 9 CPU 专家层）：进程 CPU ≈ 4.0–4.4 核**，但它的 host-GEMV 是 **2.23 ms/层**
>   （Q5_K/Q5_1 行内核 + 64 专家），9 层/token = **20.1 ms（占 45%）**。
> - **"6 个物理核 ~100%" 只在每个 0.755 ms 的 host-GEMV 突发里成立**（9 线程同时跑：3 个物理核上
>   SMT 两兄弟都忙、3 个物理核各忙 1 个兄弟）。1 秒平均后：12 个逻辑核全部落到 33–67%（实测每核中位
>   50–67%，其中约 23 个百分点来自其他 agent 后台负载），**没有任何一个核显示 100%**。
>   **≥6 核的"秒"占比实测 = 0%**（≥4 核 58–83%），这不是 bug，而是"45% 占空比 × 1 秒平均"的必然结果。

## 2. 关键对账：9 个线程在 host-GEMV 突发里确实是"满载"

| 模型 | host-GEMV/层（`last 25` 窗口） | CPU 层/token | CPU 阶段 ms/token | token 时间 | **CPU 阶段占比** | 理论 core-ms/token（9 线程） | **实测 core-ms/token**（进程 CPU × token） | 比值 |
|---|---|---|---|---|---|---|---|---|
| **35B-A3B t9** | **0.736 ms** | 24.08 | 17.7 | 39.48 ms | **44.9%** | 24.08 × 0.736 × 9 = **160** | 4.33 × 39.48 = **171** | **1.07** |
| **35B-A3B t9（复测）** | **0.755 ms** | 24.08 | 18.2 | 39.93 ms | **45.5%** | 24.08 × 0.755 × 9 = **164** | 4.30 × 39.93 = **172** | **1.05** |
| **Coder t9** | **2.227 ms** | 9.04 | 20.1 | 44.53 ms | **45.2%** | 9.04 × 2.227 × 9 = **181** | 4.04 × 44.53 = **180** | **0.99** |
| Qwen3.5-9B | —（无 CPU 层） | 0 | ~0 | 22.42 ms | ~0% | 0 | 0.98 × 22.42 = **22** | 仅主线程提交内核 |
| qwen2.5-0.5B | —（无 CPU 层） | 0 | ~0 | 6.55 ms | ~0% | 0 | 0.94 × 6.55 = **6** | 仅主线程提交内核 |

- **如果只有 1 个线程在算，实测 core-ms/token 会是 ~19（160÷9）；实测是 171–180，比值 0.99–1.07**
  （>1 的部分是主线程在 GPU 等待期间也在跑 + CUDA 驱动线程）。**这直接证明：每个 CPU 层的
  0.74–2.2 ms 里，9 个线程全部在跑。**
- 35B 的 24 个 CPU 层是连续的（MoE 层 16–39），每个 CPU 层的结构是
  `[GPU 注意力 ~0.2 ms] → [sync 等 GPU ~0.15 ms] → [host-GEMV 0.755 ms，9 线程全忙]`，
  循环周期约 1.43 ms ⇒ **CPU 在 CPU 段内的占空比 ≈ 53%，在整个 token 内 = 18.2/39.9 = 45.5%**。
  这就是"任务管理器每核只有一半"的物理来源：**PWM 式 0.755 ms 忙 / 0.67 ms 等**。

## 3. 为什么必须多线程（回答"是不是把 1 核的活拆给 9 核"）

`tools/bench_cpu_layer.exe layer 24 120`（35B 的 CPU 层形状，24 个 15.56 MB DRAM 副本轮转，
真 DRAM、非 L3，9 线程=系统默认）：

| threads | ms/层 | 聚合带宽 GB/s | 说明 |
|---|---|---|---|
| **1** | **3.262** | **5.00** | 单线程只能到 ~5 GB/s，喂不满 DRAM 的 25–30 GB/s |
| 2 | 1.835 | 8.89 | |
| 3 | 1.334 | 12.23 | |
| 4 | 1.140 | 14.32 | |
| 6 | 0.986 | 16.54 | |
| **9** | **0.752** | **21.69** | 1→9 加速 **4.34×**；每线程 2.41 GB/s |
| 12 | 0.810 | 20.14 | **反而慢 7.7%**（SMT 争 L2/L3 与执行端口） |

→ 16.31 MB 的层用 9 线程在 0.752 ms 内读完 = 聚合 **21.7 GB/s**、**每线程 2.41 GB/s**。
单线程只有 5.0 GB/s（约为 DRAM 25–30 GB/s 的 1/5），**单线程根本喂不满，所以必须多线程**；
9 线程已把本内核的算力上限（CPU-REPACK 测得的 24.8 GB/s）跑到 **88%**，再加到 12 线程超过物理核，
线程互相抢 L2/L3，聚合反降到 20.1 GB/s（−7.7%），所以实测 9 比 12 快（Coder 端到端 t12 也略慢：
45.31 vs 44.53 ms）。

## 4. 「用户感受 vs 任务管理器 vs 真实情况」

| 用户感受 | 任务管理器会显示 | 真实情况（实测） |
|---|---|---|
| 「生成时 CPU 跟待机一样，没参与计算」 | **9B/0.5B：整机 ~8%**，一个核 100%、其余接近 0 | **这是正常的**：dense 全 GPU 模型只有 1 个线程在提交 kernel（进程 0.98–1.0 核、14 个线程、无 CPU 线程池），算力在 GPU（99% util / 170 W）。 |
| 「选了 9 个线程，但看不到 9 个核满载」 | **35B：整机 ~35%，12 个核都在 40–55% 左右**，没有 100% | 真在算：**9 线程在每 token 24 次 0.755 ms 的 host-GEMV 突发里 100% 忙**（对账比值 1.05）；1 秒采样把 0.755 ms 忙 / 0.67 ms 等的 PWM 平均成 ~45% 占空比。 |
| 「CPU 阶段应该 6 个物理核 100%」 | 1 s 采样：**测不到**（实测 ≥6 核的秒占比 = 0%） | 0.755 ms 突发里 9 个逻辑核同时跑（3 个物理核 SMT 两兄弟都忙、3 个各忙 1 个）；**任何 ≥50 ms 的 OS 采样都只能看到 45–55%/核**。只有 <1 ms 分辨率或 ETW 才能看到 100%。 |

## 5. 「launcher 的线程数到底有没有传到引擎」核查

1. **launcher 命令行实证**（从运行中的 engine 进程 WMI 抓到两次）：
   `engine.exe serve … --threads 9 --cpu-int8 1 --win-priority 1 …` → **`--threads 9` 确实传了**。
2. **launcher 代码**：`src/launcher.cpp:1375 cmd += L" --threads " + wnum(g_ui.threads);`
   （每次启动都显式传）；默认值 `default_thread_count() = 1.5 × 物理核 = 9`（`src/launcher.cpp:1128-1133`），
   与引擎自己的 auto 公式 `(3×phys+1)/2 = 9` 一致。
3. **引擎侧实证（进程线程数）**：dense 模型（9B/0.5B，不用线程池）进程总线程 **14**；
   35B/Coder 在 `--threads 9` 时 **22–23**（+8–9 = 主线程 + 8 worker），`--threads 12` 时 **25–26**
   （+3 = 多 3 个 worker）。**线程数随 `--threads` 精确变化，说明设置一路传到了 `cpu::Pool`。**
4. **引擎侧实证（CPU）**：35B/Coder decode 期间进程 CPU 4.0–4.4 核，且 core-ms/token 对账 ≈ 9 线程模型
   （§2）；若 threads=1，进程 CPU 会是 ~0.5 核、对账比值 ~0.11。
5. 小瑕疵（非 bug）：`[cpu] pool threads: N` 这条日志只在 dense 的 `matvec_mt` 里打印，
   MoE 路径（`moe_forward_mt`，35B/Coder 走的就是它）不打印——建议以后给 MoE 路径也加一行
   （需要改代码，本轮按要求未改）。

## 6. 给用户的一句直白解释

> **生成时 CPU 是真的在算。** 全 GPU 的模型（9B / 0.5B）本来只用 1 个核去"发射"GPU 任务，
> 任务管理器显示 8% 是正常的，算力在 GPU 上（GPU 99%、170 W）。
> 35B 这种"部分专家层卸载到 CPU"的模型，会占用 **4 个核左右**：9 个线程在每个 token 里要分 24 段
> 各 0.75 ms 的"搬运突发"，这些突发里 9 个线程是全速的，但突发只占 token 时间的 **45%**，其余在等
> GPU。任务管理器每秒平均一次，就把"9 核 45% 占空比"抹成了"每核 40–55%"——**看起来不满载，但其实
> 该忙的毫秒一个都没少**。想判断有没有真在算，看 **GPU 利用率和 tok/s** 比看 CPU 百分比可靠得多。

## 7. 局限与说明

- 35B/Coder 测量期间后台另有 ~2.7 核负载（其它 agent 进程），已按"系统每核 − 后台估计"解释；
  严格静默环境下每核占用会各低约 23 个百分点（35B 每核约 36%）。
- 每逻辑核 % 的 50 ms 样本存在 OS 计时粒度量化（读数呈 1/6 台阶），所以**进程 CPU 用 1 s 汇总值**，
  50 ms 样本只用于看突发形态。
- 35B `--threads 12` 的端到端干净样本缺失（被并发 CUDA 进程污染，已丢弃），待用户不用机器时补测。
- 本轮曾被"用户 launcher + 我的 test_gen 同时占 GPU"污染两次（`post-load free=0` → decode 140 ms），
  已全部标记丢弃，不进入本报告结论。
