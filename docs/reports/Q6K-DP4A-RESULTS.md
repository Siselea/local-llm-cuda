# Q6_K dp4a GEMV 改造（2026-11-14）

Q5_K 的 int8 dp4a 改造（见 SPEC-COMPLIANCE.md §25）之后，9B decode 的第二大项：
Q6_K 占 2503 MB/token（≈39% 的权重流量）。本次给 Q6_K 做了同样的两级 int8 dp4a 化。

## 结果

的 `gemv_q6k`，所以 lm_head 的"旧"要按 x4 记（这也和任务书里 5.45 ms 的数字对得上）。

### 9B decode（`./build/test_gen.exe`，5 次交错运行 ×16 token，取中位）

| 配置 | decode ms/token | tok/s | 5 次 |
|---|---|---|---|

## 为什么 26 ms 是这条路径的地板

2503 MB / 330 GB/s（本机纯读天花板）= **7.58 ms**，而本机 decode 里 Q6_K 现在 8.55 ms、
其余部分（Q5_K 4053 MB ≈ 13.6 ms + attention/SSM/MoE ≈ 4.7 ms + 图开销）不变，
所以这条改造能给出的地板 ≈ **25.3–25.5 ms**；26.30 ms 已离开地板 ~0.8 ms，
缺口几乎全部来自**行数不够时的波次量化**（见下），不是内核效率。

各形状相对纯读天花板的效率：lm_head 95.5%、8192×4096 90%、4096×12288 91%、
4096×4096 86%、12288×4096 89%。lm_head 几乎贴顶，说明内核本身已经吃满 HBM。

## 实现要点

1. **一个 ql 字 + 一个 qh 字拼出两条 dp4a 字**。Q6_K 每 16 元素一组 scale，
   `x=+l` 与 `x=+64+l` 共用同一批 ql 字节（低/高 nibble）和同一批 qh 字节（bit 0-1 / 4-5），
   所以 `lane = (n2, p, g)`：p 选 A/C 或 B/D 对，g 选 4 元素组。
   每 lane 8 元素/warp 256 元素（= 1 行），16B 权重只读一次。
2. **-32 折叠进权重**：6-bit 权重 `q∈[0,63]` 用
   `((q + 0x60606060) ^ 0x80808080)`（逐字节、无进位）变成 signed int8 的 `q-32`，
   于是不需要 Q5_K 里的 `xs8 = Σx_hat` 修正项 —— 结构差异正在这里，
   Q6_K 只要 `qx` 两层 + `dx`（32 元素两级 scale），复用现成的 `quant_x_i8`。
3. **2 字节加载**：Q6_K 块长 210 B 不整除 16，块起始只有 2 字节对齐，无法用 int4 向量读；
   ql/qh/sc 都用 `unsigned short` 读（整行仍能合并成 32B sector，HBM 侧无损耗）。
4. **split-K（块内归约，无原子/无清零）**：`split` 个 warp 各拿连续一段 superblock，
   lane0 写 smem，`__syncthreads` 后由前 `warps/split` 个线程求和写 y。
   分派规则（实测）：`n_out ≤ 4096` 且 `sb_count ≥ 32 && %4==0` → split 4；
   `≥16 && %2==0` → split 2；否则 1 行/warp。
5. 缓冲全部在构造函数预分配（`qx_i8_/dx_i8_`，64K 元素上限），
   matmul 里不再 cudaMalloc → CUDA Graph capture 安全。

## 失败的尝试（都实测过）

| 尝试 | 结果 |
|---|---|
| superblock 循环 unroll 4 / 8 | 慢（4096×12288：295 → 219 / 207 GB/s），寄存器压力换不到 MLP |
| 512 线程/块 | 慢很多（网格块数减半，中等形状直接掉到 60% 占用） |
| 128 线程/块 | 与 256 持平（±1%），不值得多一套几何 |
| 2 行/warp（16 lane/行，4 chunk 全包，权重字节更省） | 与 1 行/warp 持平或更慢（8192×4096：288 vs 288） |
| split-K = 8 | 慢（每 warp 只剩 2–6 次迭代，前导开销吃掉全部收益） |
| 对 4096×4096 强行 split4 | 慢（254 vs 268 GB/s），已由分派规则规避 |
| 对 n_out ≥ 8192 强行 split2 | 慢（8192×4096：282 vs 293；lm_head：300 vs 326） |
| `__launch_bounds__(256,8)` 压寄存器 48→40 | 反而慢 1–8%（未见占用率收益） |
| 重新打包成 16B 对齐布局（未实现） | 评估后放弃：lm_head 已 95.5% 贴顶，320 字节对齐只能换来 ~5%，却要 +2.5 GB 显存或 6.7% 填充 |

**测量方法上的一个坑（值得记下来）**：最初 `bench` 连续 10 次 launch 同一个矩阵，
小矩阵（13.8 MB）会有一部分留在 3 MB L2 里，带宽被高估 10–20%，
和引擎内实测对不上（引擎里每个张量每 token 只读一次）。改成多副本轮转 + 中位后，
bench 与引擎结果一致（Q6_K 总计 8.42 vs 引擎反推 8.55 ms）。

## 剩余可做的（按性价比）

1. 更细粒度的工作单元 + 原子归约（把 8192 行的 90%、4096 行的 86% 拉到 95%+）：
   预计再省 0.5–0.7 ms，但要付清零核 + 原子 + 每单元前导，风险/收益比一般。
2. Q6_K 的 scale/d 预合并、x 两级搬 shared：预计 1–2%。
3. 真正的大头已经不在 Q6_K：Q5_K 仍有 4053 MB 按 298 GB/s 跑（13.6 ms），
   想逼近 llama.cpp 的 46.7 tok/s 要在 Q5_K（或 MoE/CPU 层）继续找。
