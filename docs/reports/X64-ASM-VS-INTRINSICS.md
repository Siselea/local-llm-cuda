# 手写 x64 汇编 vs 当前 C++ intrinsics —— 实测报告

**日期**：2026-11-27
**问题**：用 x64（汇编）会不会比现在的语言（C++17 + AVX2 intrinsics，clang 编译）更快？
**负载**：真实 35B CPU MoE 单层几何（8 路由专家 × gate/up Q4_K 512×2048 + down Q6_K 2048×512，
16.3 MB/层），12 线程（生产默认），合成量化块（block 头/scale 分布与真实权重同量级）。
**结论（一句话）**：**手写汇编相对当前 intrinsics 的实测增益是 0（在噪声内），预期区间 0–5%，
不值得维护汇编。** 但实验抓到一个**真实的、编译器层面**的 10–20% 内核增益（F16C 块头转换 +
去掉栈往返），它是 C++ 源码级、逐位相同的改动 —— 这才是应该落地的方向。

## 0. 变体与结论总表

| 变体 | 是什么 | 每 256 值块指令数（.s 静态） | phase A L3 GB/s | phase A DRAM GB/s | 相对 prod |
|---|---|---|---|---|---|

| **B f16c** | 仅把块头 fp16→fp32 换成 `vcvtph2ps` | 215（26.9） | **23.4–23.8** | **22.4–22.7** | **+11–15%** |

`2row` 因累加顺序不同有 3.05e-05 偏差（不可作为产品路径）。

**整层（A+B+merge，16.3 MB，DRAM）**：

| 组合 | 整层 GB/s（med-of-min） | 相对现行 |
|---|---|---|
| 现行：prod + i8 + merge | 18.99 | 1.00× |
| **f16c + i8f + merge** | **20.02** | **+5.4%** |
| asm + i8f + merge | 19.88 | +4.7% |
| sd + i8f + merge | 19.69 | +3.7% |
| all-fp32（对照） | 18.12 | −4.6% |

按 phase 模型（A/B 分别用实测 GB/s 折算）整层时间可降 **9.5–11.5%**（层上限，未计入 merge 固定成本）；
整层直测（含 merge 与两段之间的缓存效应）保守值 **+3.7–5.4%**。

**换算到 35B decode**：宿主 GEMV 14.81 ms/token（= 25 层 × 0.592 ms/层，本轮任务书数据）
⇒ **−0.6 至 −1.5 ms/token**（−4% 至 −10%），即 29.7 tok/s → **30.0–31.0 tok/s**。
这**不是**汇编带来的，是 F16C 块头带来的。

## 1. 方法（为什么这样测）

1. **单进程内交错所有变体**：本机是共享桌面（测量时系统 CPU 40% 被其他进程占用），
   跨进程 A/B 的分辨率只有 ±20–30%。所有变体在**同一进程、同一线程组、逐轮交错**，
   每一轮换一个**新副本**，避免上一个变体把数据拉进 L3 让下一个变体白嫖（repack 报告踩过的坑）。
2. **两个内存域**：`copies=1`（9 MB phase A 常驻 12 MB L3）分离**计算上限**；
   `copies=24`（216 MB 工作集）测**生产 DRAM 行为**。
3. **统计**：每个配置跑 5 次独立进程 × 20 轮 × 8 内层重复，报 min-of-min / med-of-min / med-p25。
   本机噪声大，**所有结论只用同进程内的相对比较**，绝对值仅作参考。
4. **线程/绑核**：生产默认是 12 线程 SMT 成对绑核，但在当前被占用的桌面上绑核实测慢 2–3 倍
   （绑死的 CPU 正好撞上其他进程），因此探针默认**不绑核**（`ENGINE_XA_AFF=0`），
   变体比较仍然公平。kernel 变体的**比值**与线程数弱相关（9/12 线程下排序一致）。
5. **源码位置**：全部实验代码在 `build/x64asm/`（`probe.cpp` + `variants.h` +
   `asmgen.py`/`asmgen_pd.py` + `count_insns.py` + `run.py`），**没有改动 `src/` 与 `tools/`**。
   probe 直接 `#include "../../src/cpu_matvec.cpp"`，所以 “prod” 就是出货内核本身。

## 2. 变体 A（基线）：现行内核实测

`avx2_dot_q4k`（4 累加器、每行入口预取本行 T0 + 下一行 T1）在 12 线程、L3 常驻下的
**计算上限**：本轮负载环境下 20.5–21.3 GB/s；同一时段 noscale（去掉全部块头）26.8–27.1 GB/s
⇒ **块头（fp16 转换 + scale 解码）占掉 ~22–24% 的算力**。纯读同字节是 100+ GB/s（L3）、
32.5–34.8 GB/s（DRAM，repack 数据）⇒ 内核**仍然是计算受限**，不是内存受限。

### 2.1 指令预算（来自编译产物 `.s`，`count_insns.py`）

Q4_K 一个 256 值块 = 144 B。executed-per-block = 外层块循环体 + (trip−1)×内层循环体：

| 变体 | 内层（g 循环）体 | 块循环体 | 每块指令数 | 每 32 值 | 备注 |
|---|---|---|---|---|---|
| prod | 44 | 150 | **282** | 35.2 | 块头 106 条：其中 **~56 条是两次分支式 `half_to_float`**（含未走到的分支），动态执行约 250 条 |
| f16c | 44 | 83 | **215** | 26.9 | 块头 39 条 |
| sd | 44 | 79 | **211** | 26.4 | 块头 35 条 |
| reg | 49 | 84 | 231 | 28.9 | vpermd + 索引物化 |
| gu | 114 | 179 | 260（+62 栈访问） | 32.5 | LLVM 展开后**溢出** |
| 2row | 114 | 179 | 260/行（+spill） | 32.5 | 8 累加器装不下（16 ymm） |
| **asm** | — | **195** | **195** | **24.4** | 全展开 g、无循环控制、无 spill |
| noscale | 39 | 45 | 162 | 20.2 | 无块头（d/dmin 被 DCE） |

**端口模型**（Comet Lake）：32×`vcvtdq2ps`（仅在 p1）+ 32×`vfmsub` + 32×`vfmadd`（p0/p1）
⇒ **p1 每块至少 64 cycle**，这是任何 fp32 实现的硬地板；实测最好内核（noscale）约 1.4× 于该地板，
差额来自 SMT 争用、端口调度与访存延迟。**继续砍指令数（211→195）没有再换来时间**，
说明瓶颈已不是指令条数/前端 —— 这是“汇编无法再加速”的核心证据。

## 3. 变体 B（源码级重构，不用汇编）

### 3.1 F16C 块头（唯一真正有效的改动）

现行 `half_to_float` 是分支式位操作（每个 144 B 块调用 2 次），因为编译目标**没有开启 F16C**：
`ziglang c++` 的默认 target features 不含 f16c（实测：`_mm_cvtph_ps` 需要 `-mf16c` 或函数级
`__attribute__((target("f16c")))`）。改用 `vcvtph2ps` 后：每块块头 106→39 条指令，
**phase A +11–15%（DRAM）/ +11–14%（L3）**，且**逐位相同**（`vcvtph2ps` 对 normal/subnormal/Inf
与位操作等价；只有 NaN payload 可能不同，权重不会是 NaN）。
两个 half（d, dmin）可以用一次 4 字节 load + 一条 `vcvtph2ps` 同时转换。

### 3.2 显式 SIMD scale 解码（sd）

LLVM 已经把 8 个 `scale_min` 自动向量化了，但仍然是“解码→写栈→块内 16 次 `vbroadcastss` 回读”。
手写 `vpshufb/vpand/vpsrlw` 解码把块头从 39 条降到 35 条，但 12 线程下与 f16c 在噪声内
（L3 23.4 vs 23.4；DRAM 21.2 vs 22.4）；9 线程下 sd 略好（31.1 vs 29.5 GB/s）。
⇒ **sd 可选，收益 0–3%，必须先 A/B 再决定**；f16c 单独就是大头。

### 3.3 多行共享激活（2row）——失败

同一层 8 个专家共享同一份激活，理论上可让 2 行共享 32 次 x 载入/块。实测 **−10%**：
2 行需要 8 个累加器（或 2 行×2 累加器时每行只剩 2 条链），加上 scale 广播与 x 载入，
超过 16 个 ymm ⇒ 溢出；`.s` 里可见 10 条 `vmovdqa` + 7–12 条 `vmovaps` 栈访问。
且它改变累加顺序（3.05e-05 偏差），产品路径也不会接受。
**结论：AVX2 的 16 个 ymm 装不下“多行 + 多累加器 + scale + x”，这条路在 Comet Lake 上关闭。**

### 3.4 2–4 路独立点积交错（ILP）——已经是现状

现行内核已有 **4 条独立累加器链**（a0..a3）。端口模型显示 p1 口（32 cvt + 32 FMA = 64 cycle/块）
是瓶颈，**不是依赖链**：noscale（把 fmsub 也去掉一半 FP）只提升 31%，而增加 ILP 的 2row/gu 反而更慢。
⇒ “隐藏 vpmaddubsw 依赖延迟”的 2–4 路交错没有新空间（production 的 int8 内核本身也有 4 条链）。

### 3.5 两级 int8（phase B 的现行路径 + F16C）

phase B（down Q6_K）现行就是两级 int8（比 fp32 快 7–9%）。给它加 F16C 块头后：
**i8f 23.0–23.2 GB/s vs i8 20.5–21.1（+10–12%）**，逐位相同。
Q4_K 的两级 int8 在 repack 轮已证明 22.7 < fp32 25.0（p1 端口被 cvt 占用率相近，没有优势），
本轮没有重复尝试。

## 4. 变体 C（手写 x64 汇编）

### 4.1 实现

`build/x64asm/asmgen.py` 生成 `asm_kernel.gen.h`：**单条 `__asm__ volatile` 实现一整行
Q4_K（n_in=2048，8 个 144 B 块）点积**，225 条指令（序言 20 + 块循环体 **195** + 归约 10）：

- `vcvtph2ps` 块头（2 条），手写 SIMD 6-bit scale 解码，结果暂存 64 B 栈后按子块广播；
- 4 组 × 2 子组**全展开**（无循环控制），累加器 ymm0–3、nibble mask ymm4、scale 广播 ymm6–9、
  转换/FMA 临时 ymm10–13，**零溢出**；
- 累加顺序与生产内核完全一致（4 累加器 + 同一归约树）⇒ **max&#124;Δ&#124; = 0.0e+00**。

调试过程本身说明了汇编的维护成本：两个 bug 花了整轮时间才定位 ——
① `vpermilps`（128-bit）会**清零 ymm 高 128 位**，用它广播 d/dmin 导致高 4 个 scale 乘 0
（需再补一条 `vbroadcastss %xmm, %ymm`）；② `vmovaps (%rsp)` 32 B 对齐要求 → 崩溃（改 `vmovups`）。
另外还写了一个“scale 在 C++ 序言解码”的隔离变体（`asmgen_pd.py`）来确认 FP 循环本身正确。

### 4.2 结果：**汇编没有更快**

| 域 | prod（C++） | 最佳 C++（f16c/sd） | **手写 asm** |
|---|---|---|---|
| phase A L3 | 20.5–21.3 | 23.4–23.8 | **22.4–23.3** |
| phase A DRAM | 19.4–20.3 | 21.2–22.7 | **21.3–21.8** |
| 整层 DRAM | 18.99 | **20.02（f16c）** | **19.88** |

asm 的指令数比最佳 C++ 少 16 条/块（195 vs 211）却**没有更快**（在噪声内互有胜负，中位数略低）。
原因就是 §2.1 的端口模型：p1 口 64 cycle/块的硬地板 + SMT/访存，指令数已不是限制。
**手写汇编能做的一切（F16C、去循环、无溢出）在 C++ 里通过 `__attribute__((target("f16c")))`
+ 简单的展开/解码写法同样能得到，而且编译器还能保证 ABI 正确性。**

### 4.3 上界估计

noscale（块头完全消失的假想实现）只到 26.8–27.1 GB/s（L3）/ 24.3–25.1（DRAM），
即 **+31% / +25%** 是“把块头成本降到 0”的上界；任何正确实现都必须做 scale 解码，
而解码成本已被证明无法通过指令数优化消除（sd 与 f16c 同速）。
汇编能贡献的额外空间 = 把 211 条的正确实现压到 195 条 ≈ **0–3%**，实测 0%。
**预期增益区间：0–5%；实测 0%。不建议维护汇编。**

## 5. 统计与噪声

- 每个数字是 5 次独立进程 × 20 轮交错 × 8 内层重复的 **med-of-min（及 min-of-min）**；
- 本报告的环境：系统 CPU 占用 40%（其他进程/桌面）；绝对 GB/s 明显低于 repack 轮
  干净窗口的 24.8（L3）/ 25.0–26.5（DRAM），但**变体排序在 4 个独立批次的测量里一致**：
  f16c/sd > asm > prod > reg/gu/2row；
- 同一变体在不同批次的 med-of-min 波动约 ±5%（如 prod L3 20.5→21.3，f16c 23.4→23.8）；
  已报告的差异（+11–15%、−8%）大于该波动。

## 6. 结论：是否值得维护汇编

**不值得。** 三条证据：
1. 现行热循环已经是 AVX2 intrinsics，与汇编是 1:1 的指令映射；LLVM 生成的内层循环
   （44 条/g，无 spill、无冗余）与手写版本逐条等价；
2. 唯一显著的成本（分支式 `half_to_float`，块头的 ~56/282 条指令）是**编译目标缺少 F16C**
   + 源码写法问题，不是“语言/编译器不够底层”：函数级 `target("f16c")` 即可解决，且逐位相同；
3. 端口模型给出的 p1 口 64 cycle/块地板，加上 SMT 争用，使“再省 16 条指令”不产生可测收益；
   手写汇编的全部潜在收益（0–5%）都低于其维护成本（ABI/clobber、n_in 特化、无跨平台、
   两次真实 bug 的调试成本）。

| # | 优化 | 证据/预期 | 预估收益（35B，每 token） |

| **1** | ✅ **已落地（§9）**：给现行内核加 F16C 块头（Q4_K fp32 + Q6_K fp32 + Q6_K int8；函数级 `target("f16c")` + 运行时回退，不改 build.sh，**逐位相同**） | phase A +11.9% DRAM，phase B +10.3%，整层 +5.4% | **−0.8 至 −1.4 ms**（14.81 → 13.4–14.0 ms GEMV） |

> 一句话给用户：**在这台机器（Comet Lake，无 AVX-512/VNNI）和这个内核形态下，
> 换 x64 汇编不会更快（0–5%，实测 0）；真正还能拿的是把 fp16→fp32 块头换成 F16C
> —— 这是 C++ 里一行函数属性的事，逐位相同、约 1 ms/token。**

## 9. 落地：F16C 块头进入生产内核（2026-11-27）

实验结论得到批准后，§7 第 1 项已实施到 `src/cpu_matvec.cpp`（单个 commit
`perf(cpu): F16C block-header decode in Q4_K/Q6_K CPU GEMV`）。

### 9.1 改动

- 三个 F16C 行内核：`avx2_dot_q4k_f16c` / `avx2_dot_q6k_f16c` / `avx2_dot_q6k_i8_f16c`。
  函数级 `__attribute__((target("f16c")))`（**不改 build.sh**），循环结构、累加器顺序与
  出货内核逐行一致，只替换块头解码（Q4_K 一次 `vcvtph2ps` 得到 d/dmin，Q6_K 一次得到 d）。
- 运行时选择：`cpu_has_f16c()` 只计算一次，`row_dot` / `row_dot_i8` 据此分派；无 F16C 回退原实现。
  检测顺序 = `__builtin_cpu_supports("f16c")` → 编译器 `<cpuid.h>` 的 `__get_cpuid(1,…) & bit_F16C`。
  **回退是必须的**：zig/clang Windows 的 compiler-rt CPU model 未初始化，builtin 对本机所有
  feature 都返回 0（实测 `f16c=0 avx2=0 sse4.2=0`），只用 builtin 会永远走旧路径、拿不到收益。
- `ENGINE_NO_F16C=1`：调试开关，强制旧实现（用于 A/B 与端到端逐位对照）。
- 未涉及 Coder 的 Q5_K/Q8_0 头部与 Q4_K 的 int8 内核（`cpu_int8=2` 才用），列为后续可选。

### 9.2 逐位验证（0 处差异）

`build/x64asm/verify_f16c.cpp`（探针 TU 直接 `#include` 生产源码，因此测的是产品路径）：

| 检查 | 结果 |
|---|---|
| 全 65536 个 fp16 bit pattern：F16C 头解码 vs 旧 `half_to_float` | **0 处 bit 不一致**（2046 对 NaN/NaN 允许 payload 不同） |
| Q4_K fp32 kernel 4096 行真实形状数据 | **0 bit mismatch** |
| Q6_K fp32 / Q6_K int8 各 16384 行 | **0 bit mismatch** |
| `tests/test_cpu_moe.exe`（默认 + `ENGINE_NO_F16C=1` 两条路径） | 均 **PASS** |
| 35B 端到端：默认 vs `ENGINE_NO_F16C=1` 生成 token id 序列 | 完全一致 |

### 9.3 收益（同进程内 A/B，生产 GEMV 路径，不受整机负载影响）

用 §1 的探针（`layer` 模式 = 生产的 `moe_forward_mt` 分段 + merge），新旧内核在**同一进程内**
逐轮交错（5 个独立进程 × 20 轮，取 med-of-min，12 线程，DRAM 域 `copies=24`）：

| 段 | 出货内核 | F16C 版 | 变化 |
|---|---|---|---|
| phase A（gate+up Q4_K fp32，9.44 MB） | 20.29 GB/s | 22.70 GB/s | **+11.9%** |
| phase B（down Q6_K int8，6.88 MB） | 21.06 GB/s | 23.22 GB/s | **+10.3%** |
| 整层 A+B+merge（16.3 MB） | 18.99 GB/s | 20.02 GB/s | **+5.4%** |

折算 35B 宿主 GEMV（任务书基线 14.81 ms/token）：phase 加权 **−9.5% → 约 13.4 ms/token**；
按整层直测（含 merge 固定成本）**−5.4% → 14.0 ms/token**。即 **13.4–14.0 ms/token，−0.8～−1.4 ms/token**。
decode（GEMV 占 ~44%）预计 **−0.4～−1.4 ms/token**。

### 9.4 端到端二进制 A/B 的环境记录（如实）

按"同一 commit、同一 flags、只差 F16C"准备了 `pre`（commit dd1c61d 干净源码）与 `new`
（dd1c61d + F16C）两个 `test_gen.exe`，在 15 分钟 GPU 窗口内交替跑 35B（`ENGINE_PROF_ACC=1`）。
但本机当时被其他 agent 的推理/CPU 任务持续占用，**pre/new 的绝对数不可用**：自适应放置从 14 层
漂到 11 层（`[placement]` 可见），CPU 争用让 `host GEMV` 在 0.67–1.18 ms/层之间漂移
（信号 ~12%，噪声更大）。因此本节的速度结论采用 **9.3 的同进程 A/B**（鲁棒），
端到端二进制 A/B 在机器安静后补测（会附在 commit 之后的消息/后续 commit 里，不挑选数据）。
端到端唯一可用的两次输出对比：pre/new 生成 token id 序列完全一致（与 9.2 的逐位结论相符）。
